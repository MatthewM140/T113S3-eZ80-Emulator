# ARMv7-A / T113-S3 Deployment Readiness

## Scope and Validation Boundary

This repository produces the standalone TI emulator process for the larger
calculator system. A separate future launcher will start and manage it. The
launcher, home UI, CAS, AI, camera, and networking applications do not belong
in this repository.

The deployable target is `calculator-emulator`. It builds without SDL3 and can
load a private external ROM, run CEmu at a wall-clock-paced 60 scheduler ticks
per second, handle `SIGINT`/`SIGTERM`, and run an unthrottled bounded benchmark.
It is currently headless because the physical T113 display and keypad stack is
not known. `ce_host` and `ce_lvgl_host` remain desktop-only development tools.

The code and the portable `ce_lvgl_app` library were cross-compiled for
ARMv7-A hard-float. The generated executable was inspected as a 32-bit ARM
EABI5 ELF. It was not run on a T113-S3, so this is readiness for first hardware
deployment, not hardware runtime validation.

## Portability Audit Findings

- The former main build blocker was CMake coupling: SDL3 was discovered for
  every CEmu build, including headless consumers. SDL discovery is now confined
  to `CE_ENABLE_DESKTOP_FRONTENDS`.
- The selected CEmu core contains no x86-only assembly. Its MSVC/x86 intrinsic
  branches are conditional and were not selected by the ARM GCC build.
- The selected Linux OS shim only provides UTF-8 file opening through libc;
  physical USB implementations and the Qt GUI are excluded.
- CEmu uses fixed-width integer types and explicit byte/bitfield-order macros.
  The build's configured little-endian order matches the T113-S3 ARM Linux
  target. A big-endian ARM build is not supported by this configuration.
- The CEmu scheduler's 64-bit arithmetic compiled and linked on 32-bit ARM
  without an extra runtime library. C11 byte/halfword/word atomics also linked
  with the toolchain's normal libc/compiler runtime.
- The public emulator API still contains no SDL, LVGL, framebuffer-device,
  DRM, or Linux-input types.
- The existing LVGL canvas wraps ARGB8888 bytes directly, which is valid for
  the validated little-endian target. Actual color/orientation/output must be
  checked again when a physical display adapter exists.
- ROM loading uses the path supplied by the caller. There is no embedded ROM,
  default repository path, home-directory lookup, or working-directory
  dependency.
- CEmu uses process-global state, which is acceptable for one emulator process;
  multiple in-process instances are not supported.

## Target ABI and Compiler Settings

Target characteristics:

- Allwinner T113-S3, dual Cortex-A7;
- ARMv7-A application profile;
- 32-bit little-endian Linux;
- EABI5 hard-float ABI;
- VFPv4 and NEON; and
- dynamically linked target libc.

`cmake/toolchains/armv7a-linux-gnueabihf.cmake` applies:

```text
-mcpu=cortex-a7 -mfpu=neon-vfpv4 -mfloat-abi=hard
```

`CE_ARM_TOOLCHAIN_PREFIX` selects the compiler prefix without the final
`-gcc`. It may be a command on `PATH` or include a path. `CE_ARM_SYSROOT` is an
optional override; normal Bootlin and Buildroot compiler wrappers infer their
own sysroot. `CE_CORTEX_A7_FLAGS` is also overridable if the final Buildroot
configuration requires a different ABI policy.

The validation used Bootlin's checksum-verified
`armv7-eabihf--glibc--stable-2026.08-1` toolchain:

```text
GCC: 15.3.0
compiler prefix: arm-buildroot-linux-gnueabihf
archive SHA-256: 9b7e25a74e87dac1e05d399444295e254a3073a056101e3197a859490e5701cd
```

This external toolchain is not vendored. The final production executable
should be rebuilt with the exact toolchain generated by the device's Buildroot
configuration so its libc, dynamic loader, kernel headers, and ABI match the
root filesystem.

The exact validation toolchain can be reproduced from Bootlin's official
archive and checksum:

```sh
curl -LO https://toolchains.bootlin.com/downloads/releases/toolchains/armv7-eabihf/tarballs/armv7-eabihf--glibc--stable-2026.08-1.tar.xz
curl -LO https://toolchains.bootlin.com/downloads/releases/toolchains/armv7-eabihf/tarballs/armv7-eabihf--glibc--stable-2026.08-1.sha256
sha256sum -c armv7-eabihf--glibc--stable-2026.08-1.sha256
tar -xf armv7-eabihf--glibc--stable-2026.08-1.tar.xz
```

## Cross-Build

After installing or extracting an ARM hard-float Linux toolchain, set its
prefix. For the validated Bootlin archive, for example:

```sh
CE_TOOLCHAIN_ROOT=/path/to/armv7-eabihf--glibc--stable-2026.08-1
CE_COMPILER_PREFIX="$CE_TOOLCHAIN_ROOT/bin/arm-buildroot-linux-gnueabihf"

cmake -S . -B build-armv7 \
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/armv7a-linux-gnueabihf.cmake \
  -DCE_ARM_TOOLCHAIN_PREFIX="$CE_COMPILER_PREFIX" \
  -DCE_ENABLE_CEMU=ON \
  -DCE_ENABLE_DESKTOP_FRONTENDS=OFF \
  -DCE_ENABLE_LVGL=ON \
  -DCE_BUILD_TARGET_APP=ON \
  -DBUILD_TESTING=OFF \
  -DCMAKE_BUILD_TYPE=Release

cmake --build build-armv7 --parallel
```

`CE_ENABLE_LVGL=ON` cross-compiles the portable LVGL application/canvas layer,
but does not create an ARM graphical executable without a target display
adapter. Set it to `OFF` for a smaller core-only cross-build. Desktop frontends
are disabled, so SDL3 is neither searched for nor linked into
`calculator-emulator`.

Install into a staging directory:

```sh
DESTDIR="$PWD/build-armv7/stage" \
  cmake --install build-armv7 --prefix /usr
```

The staged program is:

```text
build-armv7/stage/usr/bin/calculator-emulator
```

## Verified ELF Result

The validated Release build reported:

```text
ELF 32-bit LSB pie executable, ARM, EABI5 version 1 (SYSV),
dynamically linked, interpreter /lib/ld-linux-armhf.so.3
```

Relevant `readelf -h` fields were:

```text
Class:                             ELF32
Data:                              2's complement, little endian
Type:                              DYN (Position-Independent Executable file)
Machine:                           ARM
Flags:                             Version5 EABI, hard-float ABI
```

`readelf -A` reported ARMv7 application profile, VFPv4, NEON, and VFP-register
argument passing. The dynamic dependencies were only `libc.so.6` and the
hard-float loader `ld-linux-armhf.so.3`; SDL was absent.

Repeat the inspection for every production toolchain build:

```sh
file build-armv7/calculator-emulator
readelf -h build-armv7/calculator-emulator
readelf -A build-armv7/calculator-emulator
readelf -d build-armv7/calculator-emulator | grep NEEDED
```

## Standalone CLI and Process Behavior

```text
Usage: calculator-emulator --rom PATH [OPTIONS]

  --rom PATH              External private TI ROM (required)
  --revision pre-a|i|m    ASIC revision (default: i)
  --benchmark-ticks N     Run N one-tick scheduler steps unthrottled,
                          report throughput, and exit
  --help                  Show help and exit
```

Without `--benchmark-ticks`, the current target application runs headlessly at
60 CEmu scheduler ticks per wall-clock second until `SIGINT` or `SIGTERM`. It
uses no repository-relative paths and returns distinct nonzero statuses for
CLI, ROM, and runtime failures. The future launcher can pass an absolute ROM
path and manage it as a normal child process; IPC is not required yet.

Benchmark example:

```sh
calculator-emulator --rom /var/lib/calculator-emulator/ti84ce.rom \
  --revision i --benchmark-ticks 3600
```

The output includes scheduler ticks, emulated seconds, elapsed monotonic time,
ticks per second, and real-time factor. A factor of `1.0` is exactly 60 ticks
per wall-clock second. Benchmark mode deliberately calls
`ce_emulator_run(emulator, 1U)` once per tick, matching the production call
granularity while removing wall-clock throttling. Use `time -v`, `top`,
`pidstat`, or equivalent target tools for CPU and memory measurements.

## Runtime Requirements and Files

The headless target requires:

- a 32-bit ARM hard-float Linux kernel/userspace;
- a compatible target libc and `/lib/ld-linux-armhf.so.3` for the validated
  glibc build;
- POSIX monotonic clock, absolute `clock_nanosleep`, and signal support;
- the installed `/usr/bin/calculator-emulator`; and
- an external 4 MiB private TI ROM selected with `--rom`.

It requires no SDL, Qt, LVGL shared library, physical USB access, configuration
file, shell, repository checkout, or fixed current working directory. LVGL is
statically compiled only into components which use it. CEmu's physical USB
integration remains stubbed.

Recommended device placement:

- executable: `/usr/bin/calculator-emulator`;
- private runtime ROM: `/var/lib/calculator-emulator/ti84ce.rom`, mode `0600`,
  or another launcher-configured persistent-data path; and
- never place the ROM in the Buildroot source tree, target package, firmware
  image, Git repository, or release archive.

## Buildroot Readiness

Use Buildroot's generated compiler wrapper as `CE_ARM_TOOLCHAIN_PREFIX` and
keep `CE_ENABLE_DESKTOP_FRONTENDS=OFF`. A future Buildroot package can use the
standard CMake package infrastructure with these configure options and install
the single runtime binary through the project's install rule. The private ROM
must remain post-deployment user data, not a package source or installed file.

No target library package beyond the selected libc is needed for the current
headless application. Enabling a future DRM, framebuffer, or SDL target
adapter will add the corresponding Buildroot dependencies at that time. The
combined CEmu application is GPLv3; preserve CEmu's license and satisfy the
associated source-distribution obligations. Vendored LVGL is MIT licensed.

## Display and Input Boundary

Current desktop validation remains:

```text
CEmu -> emulator API -> LVGL application -> SDL3 adapter -> desktop
```

The intended target boundary is:

```text
CEmu -> emulator API -> LVGL application -> future target display adapter
physical keypad -> future Linux/platform input adapter -> emulator API
```

The portable LVGL layer cross-compiles, but no Linux framebuffer, DRM/KMS,
T113 display-engine, touchscreen, or physical-keypad adapter is claimed. Those
must be selected from actual board, panel, kernel, and input hardware facts.
SDL, LVGL, DRM, framebuffer, and Linux-input types remain outside
`ce/emulator.h`.

## First Physical-Board Procedure

1. Generate the final Buildroot toolchain and root filesystem for ARMv7-A
   Cortex-A7 hard-float. Rebuild this repository using that toolchain rather
   than copying the generic Bootlin/glibc validation binary blindly.
2. Inspect the rebuilt binary with `file`, `readelf -h`, `readelf -A`, and
   `readelf -d`. Confirm ELF32, ARM, EABI5 hard-float, and a loader/libc present
   in the target root filesystem.
3. Install the staged executable into the root filesystem at
   `/usr/bin/calculator-emulator` with mode `0755`.
4. After flashing/booting the board, copy the private ROM separately to
   `/var/lib/calculator-emulator/ti84ce.rom` and restrict it to mode `0600`.
5. Over SSH or a serial console, confirm CLI and ROM loading:

   ```sh
   /usr/bin/calculator-emulator --help
   /usr/bin/calculator-emulator \
     --rom /var/lib/calculator-emulator/ti84ce.rom \
     --revision i --benchmark-ticks 600
   ```

6. Run the representative 60-emulated-second benchmark while measuring the
   process externally:

   ```sh
   /usr/bin/time -v /usr/bin/calculator-emulator \
     --rom /var/lib/calculator-emulator/ti84ce.rom \
     --revision i --benchmark-ticks 3600
   ```

7. Record ticks/second, real-time factor, CPU utilization, maximum resident
   memory, temperature, clock frequency, and throttling state. Repeat after a
   warm-up run. Real-time TI emulation requires at least 60 ticks/second;
   additional factor indicates potential UI/system headroom but does not by
   itself prove a complete graphical workload will fit.
8. Start normal headless mode, send `SIGTERM`, and verify a clean zero-status
   shutdown before integrating it with the future launcher.
9. Only after these measurements and actual display/keypad details are known,
   select and implement the target LVGL display and Linux input adapters.

Until those steps run on the real T113-S3, runtime correctness, performance,
thermals, display output, and physical input remain unvalidated.
